# Recovered Lua regression tests

Run first-phase loading, control, and compatibility checks before later gameplay regressions:

```powershell
.\vendor\BlackBoxReborn\gradlew.bat -p tools/lua-regression stage1Test
```

This task executes the recovered entry, monitor, game worker, and HUD worker through the Lua instruction gate. It checks pause, resume, and global stop, including stop while paused. It does not run gameplay-stage tests or build an APK.

Run the recovered LuaJ task tests without configuring the Android application or building an APK:

```powershell
gradle -p tools/lua-regression test
```

The runner compiles the pure-Java Lua compatibility helpers, recovered-script tests, Lua pause/stop control tests, and screenshot fixtures. It does not apply the Android Gradle Plugin or build/install an APK.

These tests execute recovered Lua functions against controlled host callbacks and captured game screenshots. They verify script decisions and emitted actions in the test harness; they do not prove that Android OCR, screenshot capture, touch injection, sandbox launch, or the full game loop works on a device.

The recovered routines contain one static `findPic` template, `空格子0.png`; the other image paths are snapshots generated during script execution. The workbench preflight counts this template together with the Lua modules, and a regression checks that the referenced file is present.

The Android runtime waits for the sandbox game package to become the foreground activity before the first screenshot, then rejects screenshot/text/touch operations if another activity takes foreground. The recovered `showHUD` callback feeds changed script status into the existing RYLUX overlay, coalesced to avoid flooding status updates. Foreground-window delivery and overlay rendering still need device verification.

The first end-to-end LuaJ task is `recoveredBackpackScreenshotDrivesBlueSupplyPurchaseWithoutSelling`: it reads potion icons from the captured backpack screenshot, consumes observed RapidOCR count rows from `inventory-backpack-counts-rapidocr.csv`, applies the configured blue-potion threshold, and invokes the recovered seller loop. Its merchant callback models the blue-tab selection, a purchase dialog that opens at quantity 0, three increments, and dialog dismissal on confirmation; the test then verifies repair actions and that protected sale actions are absent. The same task rejects unreadable OCR without adding purchase actions. The screenshot and count rows are real captured inputs, while UI transitions and touch effects remain simulated callbacks, so this proves Lua decision/action sequencing but not on-device ML Kit or touch delivery.

The current emulator was sampled again on 2026-10-19. `localized-backpack-live-20261019.png` is the ADB screenshot with a visible small-blue-potion icon and count `1`; RapidOCR detected that count at center `(1026.00, 249.50)` with confidence `0.99998`, recorded in `localized-backpack-live-20261019-counts-rapidocr.csv`. `localizedLiveBackpackPixelsAndRapidOcrFeedRecoveredBlueSupplyScanner` feeds that screenshot and OCR row directly through the recovered Lua pixel matcher and supply decision; at configured stock threshold `3`, it returns `买蓝, 1`. This confirms the current screen geometry and localized-client sample reach the Lua buy decision. It stops before any merchant UI action, so it does not claim an actual purchase or device-side interaction.

The combat loop also evaluates configured HP/MP medicine thresholds. It accepts only a valid current/max OCR ratio with confidence at least 0.80, and taps a hotbar coordinate only after the recovered red/blue potion signature matches one of the eight game slots. LuaJ tests cover low-resource decisions, low-confidence and malformed OCR, cooldown, and the empty-slot negative case against a captured game screenshot. A positive slot-location test composites the recovered potion pixels from the real backpack screenshot into a captured gameplay frame and runs the Lua color matcher against those pixels. OCR output and touch effects are still deterministic test callbacks, so real-device OCR and touch remain unverified. Medicines must be assigned to the game's quick slots for this path to act.

Ordinary special-item sales now require the explicit sale switch, an exact item-name match in the configured allowlist, a high-confidence item count, and a count strictly greater than the configured threshold. Missing or ambiguous OCR skips the sale; eligible items pass through the recovered in-game confirmation dialog. Tests exercise both the decision policy and its connection to the seller loop. The seller name/count OCR regions still need calibration on an actual shop sale screen.

Generic purchases are connected to the recovered merchant routine. Lua scans the player's bag for each allowlisted name and requires a readable count; if a bag item name or a target count is uncertain, it skips generic purchases. It OCR-scans the captured two-column, five-row shop catalog (and its second page), maps the matching text row to the corresponding item icon, confirms the detail title, opens the purchase dialog, verifies the title and initial quantity `0`, caps the batch to the threshold gap, increments the quantity, then re-reads and verifies the final quantity before confirming. Catalog and purchase-title matching use a 0.70 OCR threshold; the saved catalog row has since been reprocessed from a 3× crop of the Chinese item name `天权冠` with RapidOCR confidence 0.99972. Destructive sale-name OCR retains the stricter 0.80 threshold. Exact allowlist matching, detail-title matching, confirmation-title matching, and quantity checks still gate the purchase. A stale or unreadable final count aborts before the purchase action. LuaJ integration tests feed OCR rows grounded in the captured screenshot and verify the emitted coordinates and confirmation sequence. The OCR callback and touches are still deterministic test callbacks, and the live exploration stopped before purchase confirmation, so ML Kit/device OCR, touch, and an actual transaction remain unverified.

The catalog OCR row in `app/src/test/resources/game/merchant-purchase-catalog-rapidocr.csv` records a fresh RapidOCR pass over a 3× crop of `merchant-purchase-list.png` (1600×900): `天权冠`, raw box center `(278.58, 160.08)`, and confidence `0.99972`. The LuaJ test reads that CSV and maps the center to the 1280×720 Lua reference point `(223, 128)`; the fixture is an observed OCR result, while the remaining callback responses are controlled test values.

The inventory count transcript was re-run with RapidOCR from the actual screenshot's small-red and small-blue count regions, enlarged 3×: `(1010,236)-(1050,269)` and `(1098,236)-(1139,269)` in the 1600×900 source image. It records the two `1` counts used by the recovered supply decision, with confidence 0.99878 and 0.99600. The LuaJ task maps those observed box centers into the requested OCR regions and rejects confidence below 0.85; Android `tomocrtextall` now applies that same 0.85 default to ML Kit rows before the Lua sees the text. This replaces the previous synthetic bright-pixel digit detector, but ML Kit still needs validation against the current device and localized UI.

The seller loop now tracks whether this run explicitly initiated an equipment or allowlisted ordinary-item sale. It confirms only a matching pending sale; a sale confirmation already open without a pending sale is closed. LuaJ tests cover the orphan-dialog case. Live sale recognition and execution remain unverified, and no live sale has been performed.

The recovered potion purchase dialog was also inspected live: it starts at quantity `0`. The Lua action loop now increments exactly N times for a configured quantity N rather than N−1; the regression test covers that observed dialog state.
