# Lua 脚本宿主实施与验收清单

## 目标

仅在用户显式点击“开始”后启动脚本。宿主加载游戏脚本及所需模块，通过截图、OCR、模板/颜色识别和无障碍触控驱动游戏；运行状态、失败原因和最近动作可观察；暂停和停止必须能中断 Lua 主线程及子线程。任何不确定的识别不得触发出售装备。

## 当前依赖矩阵

| 能力 / API | 旧脚本用途 | 当前状态 | 放行条件 |
| --- | --- | --- | --- |
| LuaJ、`require`、中文标识符兼容 | 加载封神榜、挂机、通用数据、中控及工具模块 | 已接入；加载前只重写代码里的非 ASCII 标识符，字符串/注释不变；7 个脚本模块已用 LuaJ 3.0.1 预解析 | 全部入口模块能执行初始化；异常能定位文件与行号 |
| `sleep`、`tickCount`、`beginThread`、`Thread.newThread` | 主循环、计时与状态 HUD | 指令计数钩子每 256 条 Lua 指令检查暂停/停止；共享 LuaJ VM 的函数调用串行化，`sleep` 期间让出执行权；子线程句柄支持独立 `stopThread` | 单元测试和真实脚本确认主循环、当前子线程、排队子线程都能及时暂停/停止，且无遗留工作线程 |
| `keepCapture`、`releaseCapture`、`getPixelColor` | 截图生命周期及像素读取 | 已接入基础实现 | 横竖屏、目标分辨率和截图权限实测一致 |
| `tap`、`swipe`、touch 系列 | 游戏触控 | 已接入无障碍手势 | 指定测试坐标可执行，服务中断能明确报错 |
| `findPic`、`findPicFast`、`snapShot`、`delfile` | 背包空格模板、动态区域变化检测 | 已实现初版；仅恢复一张静态模板，尚未在游戏画面校准 | 用真实截图校验匹配、掩码、坐标与相似度；不能匹配时不得点击 |
| `findColor`、`findMultiColor` | UI 提示、按钮与颜色特征检测 | 已实现初版，未设备校准 | 对真实截图验证颜色容差、边界、缩放和旋转 |
| `findMultiColorAll` | 扫描队伍列表等多个目标 | 已接入，返回 1-based 列表及 `.x` / `.y`，最多 1024 项 | 对真实截图验证旧实现坐标、容差和边界一致性 |
| `appIsRunning`、`runApp`、`stopApp` | 游戏重启与运行状态恢复 | 只查询、启动和停止白名单 BlackBox 游戏包；前台包名来自无障碍窗口事件 | 在模拟器验证多进程、后台/前台切换与重启状态 |
| `keyPress`、`imeLib` | HOME、删除输入、地图坐标文本 | HOME 通过系统全局动作；删除/输入使用当前可访问编辑节点的 `ACTION_SET_TEXT` | 游戏自绘输入框可能不暴露节点；需用地图输入流程实测，不支持时明确失败 |
| `tomocr*` / `ScriptOcr` | 物品属性、数量、队伍名称识别 | ML Kit 替代接口已接入，表格接口返回文字及屏幕坐标；精度尚未校准 | 使用真实游戏样本核对文本、坐标与置信度；低置信度拒绝交易/出售 |
| `TURING` OCR 与图像变换 | 旧字库加载、二值化、投影切割、识别 | 目前是部分兼容桩，尚不等价 | 替代实现通过样本集校准，或将调用迁移至已验证的 OCR API |
| `ui.getData`、脚本配置 | 读取工作台方案 | 只读 JSON 桥接已接入 | 所有 Lua 配置键、类型、默认值与工作台逐项对应 |
| `exec`、`restartScript`、`exitScript`、网络/文件 API | 旧脚本系统管理、远程命令和热更新 | 仅安全实现 `/proc/uptime`；任意 shell 和网络执行代码保持禁用 | 核心流程不得依赖远程命令；退出/重启必须落到本地宿主生命周期 |

## 逐阶段验收

1. **入口与依赖**：核对 APK `script.lrj`、当前恢复目录和主脚本 `require` 图；确认脚本运行不依赖缺失文件或不透明的自动更新。
2. **诊断脚本**：不自动打开游戏。通过一次显式开始执行：输出日志、截图、指定区域 OCR、模板/颜色查询、一次测试点击；再验证纯 Lua 忙循环的暂停/继续/停止、单个子线程取消、排队子线程清理及后台线程退出。LuaJ 共用一个 `Globals`，因此脚本函数串行运行；需要并行逻辑的旧脚本必须通过 `sleep` 等宿主让出点协作，真实脚本验收前不宣称并发语义等价。
3. **旧 API 兼容**：目前宿主已能进入 Lua 主入口，仍须逐项验证全部依赖的语义和返回值；未知/不可用 API 必须在操作点清楚报错，不能静默假成功。
4. **游戏样本校准**：用用户自有游戏的截图和 OCR 样本验证分辨率、缩放、横竖屏、字体和颜色。低置信度数据只能报告未知，不触发出售。
5. **核心流程**：先关闭装备/物品出售，验证登录状态、寻路、NPC 对话、战斗、补给和背包检查；然后单独验证受保护的交易流程及二次确认。
6. **发布测试包**：源代码编译通过后，构建 `2.4.26-test` / versionCode `47`，检查 APK 版本与签名，并在模拟器实际安装运行。最终验收还要求可暂停/停止、重启服务、无自动启动及无后台遗留线程。

## AI 智能体接口

Lua 宿主跑通后可作为确定性执行与状态层：提供 `getState`、`start`、`pause`、`resume`、`stop`、任务目标和事件日志的结构化桥接。智能体负责高层目标与异常决策；Lua/API 层负责低延迟的坐标、UI、循环和安全保护。只有此桥接实现并测试后，宿主才会直接提升现有智能体的执行可靠性；它不会自动赋予智能体游戏知识。
